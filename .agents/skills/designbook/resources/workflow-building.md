# Build a workflow

Used after a domain intake has identified the requested work. The agent authors the concrete task list; the CLI supplies and validates its building blocks.

1. Read effective context with `npx storybook-addon-designbook workflow discover <template>`. Inspect the template, all matched task instructions, rules, blueprints, schemas and configuration. Complete the intake's reference analysis and structural decisions. Completion: all target objects and required inputs are known.
2. Write a definition YAML following `workflow schema`. Fill `id`, `title`, `template` (source and full content), absolute `workspace_root`, effective `config`, concrete `inputs` with `inputs_schema`, embedded `context`, `schemas`, and `tasks`. Copy relevant referenced instruction material into the document too: provenance paths never become runtime load instructions. Completion: every applicable instruction and schema is embedded.
3. Author each task explicitly: stable unique `id`, `title`, `type`, concrete `target`, `depends_on`, `params`, `params_schema`, predecessor `inputs`, embedded `instructions`, internal `context` references and `outputs`. Resolve every structural parameter and output path now. Turn repetition hints into concrete tasks yourself. Include prerequisite CSS/setup work when needed. Completion: the complete ordered dependency graph and rule assignment are fixed.
4. Each output declares `required`, embedded JSON `schema`, `submission: data | direct`, `validators`, and an absolute `path` for file outputs. Carry every applicable file validator from the discovered result contract into the output, including executable checks for generated source. Move prepare-time schema queries into intake and embed their results. Embedded schemas use internal references only. Carry instructions for authored generators in context; generator artifact paths are explicit outputs. Completion: every task has a complete, enforceable result contract.
5. A task may read a known predecessor result through `inputs: { name: { task: predecessor-id, result: output-key } }`. These values supply artifact content, never target selection, dependencies, task counts or rule assignment. Include the predecessor in `depends_on`. Completion: every result reference names a declared output on a predecessor.
6. Run `workflow validate <definition.yml>`, correct all reported definition errors, then `workflow create <definition.yml> --output <run-path>`. Use `$DESIGNBOOK_DATA/workflows/changes/<unique-run-id>/tasks.yml` for Storybook visibility. Completion: the CLI returns the path of a newly persisted document containing its fixed definition and initial state.
7. Invoke `execute-workflow <run-path>` immediately. Completion: the executor has completed the fixed tasks or recorded a concrete, resumable blockade.

Use JSON result files for CLI submission. Keep field names aligned with `workflow schema`; it is the canonical machine contract. Config instructions are content in the YAML, not paths to reread from config during execution.
