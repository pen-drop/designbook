# Plan complete writes

1. Inspect the selected existing artifacts and usages. Embed relevant existing source content in `definition.context` entries and reference those entries from each consuming task, including baselines for files that must remain untouched. Keep concrete source paths, identities and preservation criteria in definition inputs/task parameters. Context content can carry literal template syntax; structural inputs and parameters must be fully concrete. Record the exact delta and semantic preservation criteria; use byte/hash checks for whole unchanged files. Completion: target identity and baseline are unambiguous.
2. Apply the shared builder's source reference prerequisite before deriving implementation decisions. Decide component decomposition, target structure, styling, assets and behavior from the bound observations; for reference-free requests, use concrete appearance, behavior and responsive criteria plus retained structure. Completion: execution needs no new reference, asset or structural selection.
3. Enumerate all target IDs, paths, variants, stories, mappings, sample changes and consumer edits. Distinguish verification-only consumers. Assign `scene_scope` from the actual scene target and embed applicable screen/shell rules for consumer follow-ups. For every component story in scope, freeze identity as `namespace` + `group` + `component` + `variant`, then **derive** the CSF story id and story URL from that identity via the active component-framework story-address rule (SDC: `sdc-components`; Vue: `vue-components`). Retained existing stories keep the exact id from the live index. Present the selector inventory to the user as a table before execution: subject, native reference locator (or no reference), story selector, views, explicit breakpoint mappings and observed reference evidence. Use one row per exact subject ID and summarize all of its states and breakpoints in that row. In the evidence cell, associate each observed state and breakpoint with its screenshot path and a short description of what the user can see; an expanded menu remains a state of the same subject. Label story selectors for new markup as planned; distinguish them from selectors checked against existing DOM. Include every comparison subject and resolve ambiguous matches before proceeding. This presentation is part of intake even when the request asks to execute without questions. For a design-entity, design-component, design-screen or design-shell plan, the complete task list includes a composition snapshot of baseline components, mappings, samples, scenes and data_model — empty arrays when nothing is reused. Follow the shared builder for tree presentation and execution order. Completion: the user-visible intake accounts for every subject, state and breakpoint with concrete source locators, implementation selectors and evidence, and every necessary write and affected story URL is accounted for — with every planned CSF id matching the derived address for its frozen identity.
4. Apply [the component prerequisites rule](scenes-constraints.md) to every creation or change that writes components. Plan the graph in batches: component writes → `refresh-components` → mapping/scene writes → final build and browser verification. Bind each mapping/scene task to the refreshed index through predecessor inputs from the shared builder. Embed the union of retained live-index story ids and **derived** planned component story ids before execution; refreshed inventory supplies known artifact data only. Always start the live Storybook with `storybook start` — it assigns a free port and records it in `$DESIGNBOOK_DATA/storybook.json`; resolve every `index_url` and story URL from the running server (`storybook status`), never a static config URL or fixed port. Completion: inspect every mapping/scene task's dependency chain and index input; its refresh follows all component writes in the batch, and its `index_url` is the live `storybook status` URL. A final build alone cannot satisfy this prerequisite.
5. Declare actual `pnpm build-storybook` evidence and `storybook check <story-url>` tasks for concrete affected URLs, with exact viewport, selector, interaction and semantic observations from the request. Cover preserved variants and affected consumers as well as changed output. Completion: successful command results and browser observations establish every acceptance criterion; transcript keywords or empty result collections are insufficient.

Preservation uses the existing artifact as baseline; blueprint defaults guide new structure. Retain identities unless an explicit rename includes all reference changes. Missing requirements discovered in execution block the saved run; a new intake must resolve them before a new fixed definition can run.
